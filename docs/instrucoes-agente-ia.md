# Configuração do Agente de IA — SetFlow\n\nInstruções e convenções para o agente de codificação (Cursor, Claude Code, VS Code + Copilot ou similar) durante o desenvolvimento do SetFlow segundo SDD.\n\n## Instrução Principal\n\nO agente de IA deve:\n1. **Consultar sempre a baseline em `/docs`** antes de gerar ou modificar código.\n2. **Seguir rigorosamente a Spec ativa** sem adicionar comportamentos, bibliotecas ou dependências não aprovados.\n3. **Registrar lacunas técnicas como OPEN-XX** na Spec, sem tomar decisões silenciosas.\n4. **Acompanhar código com testes unitários** que comprovem os critérios de aceite (Dado, Quando, Então).\n5. **Manter rastreabilidade** entre código, Spec, requisitos e modelo de domínio.\n\n## Contexto Operacional\n\n### Estrutura do Repositório\n```\nSetFlow/\n├── docs/\n│   ├── visao.md                      # Visão do produto\n│   ├── personas.md                   # Personas\n│   ├── requisitos.md                 # RF, RB, RNF\n│   ├── modelo-dominio.md             # Modelo conceitual\n│   ├── arquitetura.md                # Estilos e drivers\n│   ├── arquitetura-decisoes-aprovadas.md  # ADRs e abertos\n│   ├── adrs/\n│   │   └── ADR-001-algoritmo-ordenacao-setlist.md\n│   ├── casos-de-uso/\n│   │   ├── UC-01-gerar-setlist.md\n│   │   └── UC-01-montar-e-confirmar-setlist.md\n│   ├── uml/\n│   │   ├── estados-setlist.md\n│   │   └── seq-UC-01.md\n│   └── specs/\n│       ├── mapa-de-specs.md\n│       ├── SPEC-001-autenticacao-identidade-usuario.md\n│       ├── SPEC-002-criacao-banda-membros-contexto.md\n│       ├── SPEC-003-gestao-repertorio-configuracao.md\n│       ├── SPEC-004-criacao-setlist-rascunho.md\n│       ├── SPEC-005-sugestao-automatica-ordem.md\n│       ├── SPEC-006-reordenacao-confirmacao-setlist.md\n│       ├── SPEC-007-visualizacao-setlists-dominio.md\n│       └── SPEC-008-ciclo-vida-historico-setlist.md\n├── src/\n│   ├── index.js (ou main.ts)         # Ponto de entrada\n│   ├── models/                       # Entidades de domínio\n│   ├── services/                     # Lógica de negócio\n│   ├── repositories/                 # Acesso a dados\n│   ├── middlewares/                  # Autenticação, validação\n│   └── routes/                       # Endpoints da API\n├── tests/\n│   └── [testes unitários e de integração]\n├── package.json                      # Dependências (Node.js)\n├── CLAUDE.md                         # Diretivas do agente (este arquivo)\n└── README.md                         # Visão geral do projeto\n```\n\n### Stack Tecnológico (Aprovado)\n- **Linguagem:** Node.js + TypeScript\n- **Frontend:** HTML5 + CSS3\n- **Banco de Dados:** PostgreSQL\n- **Versionamento:** Git + GitHub\n\n### Convenções de Desenvolvimento\n- **Idioma:** Português (documentação e comentários de código)\n- **Nomenclatura:** snake_case para variáveis de banco, camelCase para JavaScript\n- **Commits:** formato convencional (feat, fix, docs, test, refactor, etc.)\n- **Branches:** seguir a convenção do projeto (sdd-spec-preparation para specs, feature/SPEC-XXX para implementação)\n\n## Fluxo de Trabalho do Agente\n\n### Fase 1: Leitura e Compreensão\n1. Quando iniciar, leia a Spec ativa (ex: SPEC-001) completamente.\n2. Valide as pré-condições, dependências e Definition of Done.\n3. Consulte o modelo de domínio para garantir consistência.\n4. Verifique as regras de negócio (RB-XX) aplicáveis.\n5. Confirme os critérios de aceitação (Dado, Quando, Então).\n\n### Fase 2: Análise de Lacunas\n1. Se algum detalhe técnico não estiver definido na Spec, registre como OPEN-XX.\n2. Não invente padrões, formatos ou tecnologias não aprovados.\n3. Se a lacuna bloquear a implementação, suspenda e reporte para decisão humana.\n\n### Fase 3: Implementação\n1. Implemente apenas o comportamento descrito na Spec.\n2. Mantenha separação clara entre camadas (apresentação, aplicação, persistência).\n3. Aplique DA-02 (isolamento por banda) em toda operação de acesso.\n4. Valide entradas e saídas conforme contratos da Spec.\n5. Use types TypeScript para garantir segurança de tipos.\n\n### Fase 4: Testes\n1. Crie testes unitários para cada critério de aceitação.\n2. Use a estrutura Dado-Quando-Então (BDD) quando possível.\n3. Teste também invariantes (INV-XX) definidas na Spec.\n4. Valide isolamento por banda em testes de segurança.\n\n### Fase 5: Documentação\n1. Adicione comentários explicativos em código complexo.\n2. Documente qualquer desvio da Spec como divergência explícita.\n3. Atualize o arquivo de questões em aberto se identificar novos gaps.\n4. Mantenha rastreabilidade de RF/RB/RNF no código.\n\n## Regras Obrigatórias\n\n### Segurança\n- [ ] Toda operação sensível exige autenticação (SPEC-001)\n- [ ] Filtro de banda_id é obrigatório (DA-02)\n- [ ] Senhas armazenadas em hash (RNF-03)\n- [ ] Proteção contra CSRF e XSS (RNF-03)\n- [ ] Nenhum dado de outra banda deve vazar\n\n### Consistência\n- [ ] Modelo de domínio (entidades, relacionamentos) respeitado\n- [ ] Regras de negócio (RB-XX) nunca violadas\n- [ ] Estados do domínio (ex: Rascunho → Confirmado → Tocado) preservados\n- [ ] Invariantes (INV-XX) verificáveis após cada operação\n\n### Performance\n- [ ] Ações principais respondem em <2 segundos (RNF-01)\n- [ ] Algoritmo de ordenação roda em <2s para até 50 músicas (DA-03)\n- [ ] Sem queries N+1; otimizar acesso a banco\n\n### Rastreabilidade\n- [ ] Cada classe/função tem comentário de qual RF/Spec a implementa\n- [ ] Testes referenciam critérios de aceitação\n- [ ] Commits linkam a Specs e PRs\n\n## Integração com Ferramentas de IA\n\n### Cursor (Recomendado para SDD)\n1. Configure `.cursorules` ou `.cursorrules` na raiz do projeto:\n   ```\n   # Cusso Rules para SetFlow\n   \n   You are implementing SetFlow, a music setlist manager for bands.\n   \n   ALWAYS:\n   - Check /docs/specs/SPEC-XXX.md before implementing\n   - Follow the exact behavior described in the active Spec\n   - Apply DA-02 (band isolation) to all data access\n   - Write tests for each Dado-Quando-Então criterion\n   - Use TypeScript types for type safety\n   - Never add features not in the Spec\n   - Register gaps as OPEN-XX in the Spec\n   - Preserve business rules (RB-XX) and invariants (INV-XX)\n   \n   Domain Model (from /docs/modelo-dominio.md):\n   - Usuario: id, nome, email, senha_hash\n   - Banda: id, nome, limiar_transicao_semitons\n   - Membro: id, usuario_id, banda_id, papel\n   - Musica: id, banda_id, titulo, tom, bpm, duracao_segundos, observacoes, cifra_anexo\n   - Setlist: id, banda_id, nome, data, tempo_disponivel_segundos, estado\n   - ItemSetlist: id, setlist_id, musica_id, ordem\n   - DominioMusica: id, usuario_id, musica_id, nivel\n   ```\n\n2. Use o painel de referência do Cursor para manter `/docs/specs` sempre visível.\n\n### Claude Code (GitHub Copilot + Claude)\n1. Forneça como contexto a Spec ativa e o modelo de domínio.\n2. Use o comando `@github` para linkeditar PRs e issues a Specs.\n3. Peça ao agente para \"Garantir que o código segue SPEC-XXX.\"\n\n### VS Code + Copilot\n1. Mantenha a Spec aberta em uma aba separada.\n2. Use comentários de Spec-Driven Development:\n   ```typescript\n   // SPEC-001: Validar credenciais e iniciar sessão\n   // RF-01: Autenticação\n   // RNF-03: Senhas em hash\n   ```\n\n## Camadas de Segurança do Ambiente de Desenvolvimento\n\n### 1. Segurança de Código Fonte\n- **GitHub:** repositório privado\n- **Branches protegidas:** main exige 1 review antes de merge\n- **Secrets:** não commitam credenciais; usar GitHub Secrets para env vars\n- **CODEOWNERS:** arquivo que define responsáveis por áreas críticas\n\n### 2. Segurança em Tempo de Desenvolvimento\n- **ESLint + Prettier:** validação de código e formatação\n- **TypeScript strict mode:** type safety obrigatório\n- **Pre-commit hooks:** testes e lint rodam antes de commit\n- **No credentials in code:** credenciais são injetadas via variáveis de ambiente\n\n### 3. Segurança em Tempo de Teste\n- **Testes unitários:** validam regras de negócio e isolamento\n- **Testes de segurança:** verificam DA-02 (isolamento por banda)\n- **Testes de integração:** validam fluxo completo end-to-end\n- **Coverage mínimo:** 70% de cobertura obrigatória\n\n### 4. Segurança em Tempo de Deploy\n- **CI/CD (GitHub Actions):** pipeline validar sintaxe, rodar testes, gerar build\n- **Environment variables:** credenciais injatadas de forma segura\n- **Database migrations:** rollback automático em caso de falha\n- **HTTPS obrigatório:** todas as comunicações criptografadas\n\n### 5. Segurança em Tempo de Execução (Produção)\n- **Autenticação:** SPEC-001 implementada, validação em toda rota protegida\n- **Autorização:** RB-04, RB-07 preservadas; acesso por papel e banda\n- **Rate limiting:** proteção contra brute force (OPEN-XX a decidir)\n- **Logging:** rastreamento de ações sensíveis para auditoria\n- **Monitoramento:** alertas em caso de anomalias ou erros frequentes\n- **Backup:** cópias periódicas de dados (OPEN-XX a definir estratégia)\n\n### 6. Segurança de Dados em Trânsito\n- **HTTPS:** TLS 1.3 obrigatório\n- **CORS:** apenas domínios conhecidos autorizados\n- **CSRF tokens:** validação em operações de estado (POST, PUT, DELETE)\n- **XSS prevention:** sanitização de entrada e escaping de saída\n\n### 7. Segurança de Dados em Repouso\n- **PostgreSQL:** autenticação obrigatória, senhas não compartilhadas\n- **Hash de passwords:** bcrypt ou Argon2 com salt aleatório\n- **Criptografia de campos sensíveis:** considerar para futuras evolu��ões\n- **Backup encriptado:** dados de backup criptografados\n\n## Checklist de Segurança para o Agente\n\nAntes de considerar uma Spec implementada, valide:\n\n- [ ] Toda entrada foi validada (tipos, tamanho, formato)\n- [ ] Toda saída foi sanitizada (sem exposição de detalhes técnicos)\n- [ ] DA-02 foi aplicada em todo acesso a dados\n- [ ] Autenticação foi verificada em rotas protegidas\n- [ ] Autorização foi verificada (papel, banda)\n- [ ] Senhas não são armazenadas em texto claro\n- [ ] Tokens/sessões são únicos e associados ao usuário correto\n- [ ] Logs não contêm credenciais ou dados sensíveis\n- [ ] Testes validam cenários de segurança (acesso indevido, isolamento)\n\n## Comunicação com Agentes de IA\n\n### Prompt Padrão para Iniciar Implementação\n```\nVou implementar [SPEC-XXX] — [Nome da Spec].\n\n1. Leia `/docs/specs/SPEC-XXX.md` completamente.\n2. Valide pré-condições e dependências.\n3. Implemente apenas o comportamento descrito na Spec.\n4. Crie testes para cada critério de aceite (Dado-Quando-Então).\n5. Mantenha isolamento por banda (DA-02) em todas as operações.\n6. Não adicione funcionalidades não descritas na Spec.\n7. Registre lacunas como OPEN-XX se encontrar alguma.\n8. Preservar RB-XX e INV-XX definidas na Spec.\n```\n\n### Sinais de Alerta\nSe o agente:\n- Adicionar dependências não aprovadas → pare e valide\n- Violar DA-02 (isolamento por banda) → rejeitar e refatorar\n- Não gerar testes → pedir cobertura de critérios de aceite\n- Implementar comportamento fora da Spec → questionar e revisar\n\n## Próximos Passos\n\n1. **Antes de começar SPEC-001:**\n   - Decidir as questões em aberto com prioridade Alta\n   - Validar padrão de API e estratégia de autenticação\n\n2. **Durante implementação:**\n   - Manter este arquivo atualizado com novas restrições\n   - Comunicar OPEN-XX descobertos durante desenvolvimento\n\n3. **Após implementação de cada Spec:**\n   - Validar Definition of Done\n   - Atualizar checklist de segurança\n   - Documentar qualquer desvio ou aprendizado\n"
